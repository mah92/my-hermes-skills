# Hermes Bot Containers (family bots on Bale/Telegram)

## When to Use

- Setting up a new isolated Hermes bot profile for another person (family/friends) on Bale or Telegram.
- Recreating/repairing a containerized bot (`hermes-<bot-name>`) after config or mount changes.
- Diagnosing broken voice (STT or TTS) or missing models inside a containerized profile.
- Answering "why did the container download a model / why doesn't voice work in the container".

## Design: path mirroring (v2 — the whole point)

The container is a **mirror of the host filesystem layout**. Every path used by the
main system resolves to the same string inside the container, so a copied `.env` and
`config.yaml` work **VERBATIM** — TTS/STT commands, model paths, everything — and
nothing ever needs path rewriting:

- `HOME=/home/oem` and `HERMES_HOME=/home/oem/.hermes` (overrides the image default `/opt/data`)
- The profile dir is mounted AT `/home/oem/.hermes` (host: `~/.hermes/profiles/<name>`)
- `/home/oem/hermes_files`, `/home/oem/Basir`, `/home/oem/.hermes/hermes-agent/venv`,
`/home/oem/.local/share/uv` are mounted ro at their host paths
- `/home/oem/workspaces/<name>` is mounted rw at the same host path
- Profile-internal symlink: `~/.hermes/models -> /home/oem/hermes_files/sherpa-onnx-en-stt`

Verified (2026-08, disposable test container): `python3 ~/.hermes/skills/hermes-persian-tts/scripts/tts.py`
and `/home/oem/.hermes/hermes-agent/venv/bin/python /home/oem/.hermes/skills/hermes-persian-stt/scripts/stt.py` — both run
unchanged inside the container and produce audio/transcripts.

## Runtime access model (accepted by Ali)

- **Passwordless `sudo` inside the container** (derived image `hermes-agent-sudo`).
  Container-root only: no docker socket, host mounts are ro, default seccomp/caps,
  isolated PID ns → no host escape. Residual: `network_mode: host` + NET_RAW means
  container-root can use raw sockets on the host LAN — accepted for the trusted
  family setup. Rebuild the image via `scripts/sudo-image.Dockerfile`.
- **The bot user can read its own profile `.env`** (owner uid 1000, mode 600) — by
  design: the gateway loads it at boot and the shared avalai/DeepSeek LLM keys are
  accepted as readable by each bot. The Bale token stays UNIQUE per bot.
- **Each bot's `.env` is separate and adjustable from the host** at
  `~/.hermes/profiles/<name>/.env`; `docker restart hermes-<name>` applies changes.

## Quick start — the script

```bash
# ONE command adds a whole bot (profile + skills + .env + compose service + container):
~/.hermes/skills/system-admin/hermes-bot-containers/scripts/add-bot.sh \
  <name> --token <BALE_TOKEN> --user <USER_ID> [--admins <ID1,ID2>] \
  [--compose-file ...] [--no-start]
```

Remove a bot (container + profile + workspace + compose service): `scripts/rm-bot.sh <name>`.

See the script header for all options. The script does: profile dirs + workspace →
.env copied from main (Bale token/user swapped, secrets stripped if present) → skills rsync as
REAL copies with `models/` symlinks re-created → config.yaml generated from the main
config (platforms/toolset/api_server/terminal/plugins/tts/stt/session_reset
overrides) → compose service appended
→ container up → venv-ai with `mcp<2`. `--no-start` skips the last two.

Security note: prefer `BALE_TOKEN` env var or `read -r -s` over argv on multi-user
hosts (`--token` is visible in process listings). The token never lands in the
compose file — only in the profile `.env` (mode 600).

```
/home/oem/profiles-containers/docker-compose.yaml   <- one service per bot, generated by add-bot.sh
/home/oem/.hermes/profiles/<name>/                  <- profile = container ~/.hermes (mounted rw)
/home/oem/workspaces/<name>/                        <- container working dir, same path (rw)
/home/oem/hermes_files/                             <- single shared store, mounted ro at same path:
    hermes-persian-stt/models/                          shenava-koochik + hush_cpp
    hermes-persian-tts/models/                          matcha-fa_en-zahra-22050-5.onnx, vocos22.onnx, tokens_sherpa_with_fa.txt
    sherpa-onnx-en-stt/                                 paraformer-en (~220M) + streaming-zipformer-en (~70M)
    tts-libs/                                           libonnxruntime.so.1, libespeak-ng.so.1, libicudata.so.70, libicui18n.so.70, libicuuc.so.70
/home/oem/Basir/                                   <- MatchaTTSInfer, espeak-ng-data (at the ESPEAK_DATA path from .env) (ro)
/home/oem/.hermes/hermes-agent/venv/               <- hermes-agent venv, mounted ro - runs STT (shenava stt.py) verbatim
/home/oem/.local/share/uv/                         <- real interpreter behind the venv symlink, mounted ro
```

- Main system points at the same EN store: `/home/oem/.hermes/models -> /home/oem/hermes_files/sherpa-onnx-en-stt`.
- `.agents` is the older skills location; main skills like `hermes-persian-tts` are
  symlinks `-> ../../.agents/skills/...` — RELATIVE, so copying them naively produces
  dangling links in the profile. The script rsyncs with `-L` (dereference) and
  re-creates `models/` links afterwards.

## Manual steps (same as the script)

1. **Profile**: `mkdir -p ~/.hermes/profiles/<name>` (or `hermes profile create <name>`).
2. **.env**: copy main `.env`; swap `BALE_BOT_TOKEN`, `BALE_HOME_CHANNEL`,
   `BALE_ALLOWED_USERS`/`CHATS` (owner + any extra admins, explicitly); scrub secrets:
   `SUDO_PASSWORD`, `BROWSERBASE_*`, `EXA_API_KEY`, `PARALLEL_API_KEY`, `FAL_KEY`,
   `FIRECRAWL_API_KEY`, `OPENROUTER_API_KEY`, `VOICE_TOOLS_OPENAI_KEY`, `GROQ_API_KEY`,
   `ELEVENLABS_API_KEY`. Keep the avalai LLM key + `DEEPSEEK_API_KEY` + Bale + TTS/STT lines.
   `HERMES_LOCAL_STT_COMMAND` stays the MAIN value (host paths = container paths now).
3. **Skills + plugins**: `rsync -aL --delete` main skills (dereference all links), EXCLUDING
   `models/` links — discover them with `find . -type l -name models` PLUS a check
   for `*/models` inside top-level skill symlinks (`hermes-persian-tts` itself is a
   link, so plain `find` misses its `models/`) — then re-create those links
   (targets are absolute into hermes_files). Copy `plugins/` too (`rsync -a
   --exclude='.git/'`) — the Bale platform adapter lives there and the gateway
   CANNOT start the platform without it (a real bug hit during rebuild testing).
4. **Memory/soul**: fresh profile = no admin data; do not copy main memories.
5. **config.yaml**: generated from main's config with these overrides:
   - `platforms: {api_server: {enabled: false}}`
   - `platform_toolsets.bale`: 15 tools, no `cronjob` (browser, clarify, code_execution,
     computer_use, delegation, file, image_gen, memory, session_search, skills, terminal,
     todo, tts, vision, web)
   - `plugins.enabled: [platforms/bale]` (list form!) + memory-store db at
     `/home/oem/.hermes/memory_store.db`
   - `terminal.cwd: /home/oem/workspaces/<name>`
   - TTS/STT provider commands: the MAIN-style `~/.hermes/skills/...` strings,
     semantics mirror works, e.g. `shenava` command = `/home/oem/.hermes/hermes-agent/venv/bin/python
     /home/oem/.hermes/skills/hermes-persian-stt/scripts/stt.py --quiet {input_path}`
   - `mcp_servers.comfy-flux`: `command: /home/oem/.hermes/venv-ai/bin/python`,
     `args[0]: /home/oem/.hermes/mcp/comfy-flux/server.py` (server file copied into
     the profile — the main config's `~/.hermes/mcp` path would NOT resolve in a
     fresh container)
   - `_config_version` is inherited from the main config; the gateway migrates it on
     first boot (writes `config.yaml.bak`/`.env.bak`) — expected, not a bug.
6. **Compose service** (appended by the script; `network_mode: host` for localhost
   MCP: Firecrawl :3002, comfy-flux):

```yaml
  <name>:
    image: nousresearch/hermes-agent-sudo:20260827    # official image + passwordless sudo (scripts/sudo-image.Dockerfile)
    container_name: hermes-<name>
    restart: unless-stopped
    network_mode: host
    working_dir: /home/oem/workspaces/<name>
    environment:
      - PUID=1000
      - PGID=1000
      - HERMES_UID=1000
      - HERMES_GID=1000
      - HOME=/home/oem
      - HERMES_HOME=/home/oem/.hermes
      - HERMES_WRITE_SAFE_ROOT=/home/oem
      - HERMES_LAZY_INSTALL_TARGET=/home/oem/.hermes/lazy-packages
      - API_SERVER_ENABLED=false
      - LD_LIBRARY_PATH=/home/oem/hermes_files/tts-libs
    volumes:
      - /home/oem/.hermes/profiles/<name>:/home/oem/.hermes
      - /home/oem/hermes_files:/home/oem/hermes_files:ro
      - /home/oem/Basir:/home/oem/Basir:ro
      - /home/oem/miniconda3:/home/oem/miniconda3:ro
      - /usr/lib/locale:/usr/lib/locale:ro
      - /usr/share/i18n:/usr/share/i18n:ro
      - /home/oem/workspaces/<name>:/home/oem/workspaces/<name>
    command: ["gateway", "run"]
    mem_limit: 4g
```

7. **Once per container**: `python3 -m venv ~/.hermes/venv-ai` (inside, as user
   `hermes`) + `pip install "mcp<2"` — only needed for MCP servers; STT uses the
   mounted conda env. The script does this automatically.

```bash

docker exec -u hermes hermes-<name> bash -lc 'ls /home/oem/.hermes/models/'   # shared EN store, ro

docker exec -u hermes hermes-<name> bash -lc '
  set -a; source ~/.hermes/.env; set +a
  echo "سلام تست" > /tmp/in.txt
  python3 ~/.hermes/skills/hermes-persian-tts/scripts/tts.py --speed 1.0 /tmp/in.txt /tmp/out.ogg

grep "Connected as" /home/oem/.hermes/profiles/<name>/logs/agent.log | tail -1   # Bale connected
```

## Pitfalls (each one cost a debugging session)

1. **Image defaults**: the official image sets `HERMES_HOME=/opt/data` and
   shell `HOME=/root`. Override BOTH via compose — otherwise `~/.hermes/skills/...`
   commands and `~/.hermes/models` downloads land in the wrong place (duplicate
   220MB model download happened exactly this way).
2. **Relative symlinks in main skills** (`hermes-persian-tts -> ../../.agents/...`):
   they resolve from the skills dir depth; inside `profiles/<name>/skills` they
   dangle. Always rsync `-L` and re-link `models/` AFTER (targets are absolute into
   hermes_files, so they work in-container because hermes_files is mounted at the
   same path).
3. **Copying .env verbatim is safe now** — except tokens/secrets must still be
   swapped/stripped. Do NOT delete `HERMES_LOCAL_STT_COMMAND` or change its value.
4. **MatchaTTSInfer** needs host-built shared libs (onnxruntime, espeak-ng, ICU 6x):
   `hermes_files/tts-libs` + `LD_LIBRARY_PATH`; plus host `/usr/lib/locale` +
   `/usr/share/i18n` ro mounts or the C++ daemon aborts on `std::locale`.
5. **`pip install mcp` (v2)** breaks `from mcp.server.fastmcp import FastMCP` → pin `"mcp<2"` in venv-ai.
6. **Stale daemon socket after `docker restart`**: /tmp persists; `tts_infer.sock`
   from the dead daemon → Connection refused. Hardened tts.py probes the socket,
   unlinks and restarts the daemon. Keep the hardened copy in sync (main skills +
   every profile copy).
7. **"Previous gateway life exited UNCLEANLY"** after `--force-recreate` is EXPECTED (SIGKILL of the old container).
8. **`hermes config set plugins.enabled`** may write a string instead of a list →
   gateway breaks; verify with grep; repair with python yaml.
9. **Gateway initializes the profile** on first boot (SOUL.md, backups/, cache/,
   channel_directory.json, gateway.pid) — that is NORMAL, not corruption.
10. The gateway writes `.env.bak`/`config.yaml.bak` at boot — the profile needs rw,
    everything else shared is ro.
11. Test scripts dropped into container `/tmp` vanish on recreate — keep them on the host.
12. `docker restart` reloads config/.env; `--force-recreate` needed only for mount/env changes.
13. **Copying main's sessions/memory into a profile**: the bot gateway RESUMES the most recent OPEN session from state.db at boot and replays its dangling tool calls — it will continue the main agent's in-flight work (writing files, sending messages to main's chats). ALWAYS close open sessions in the copy BEFORE boot: `UPDATE sessions SET ended_at=?, end_reason='completed' WHERE ended_at IS NULL`, and clear `gateway_routing` (DELETE FROM gateway_routing) so the bot re-registers its own chats. History stays searchable; only resume pointers are dropped.
14. **Live SQLite copies**: main's state.db/memory_store.db are WAL-backed and written continuously. Never `cp` them — use Python's `sqlite3` backup API (`src.backup(dst)`) or `VACUUM INTO` for a consistent snapshot; remove the target's stale `-wal`/`-shm`/lock files when overwriting. Verify after: `PRAGMA integrity_check` + row counts (facts/sessions/messages) inside the container.
15. **venv-ai is container-ABI-specific**: creating it on the host breaks in-container (host python 3.11 vs image 3.13 → `bin/python` symlink dangles). Create it INSIDE the container (`docker exec -u hermes hermes-<name> python3 -m venv ~/.hermes/venv-ai`). If PyPI is unreachable in-container, download cp313 wheels on the host via the socks proxy and install offline: `pip download "mcp==1.28.1" --only-binary=:all: --platform manylinux2014_x86_64 --python-version 3.13 --abi cp313 --implementation cp -d wheels/`, copy wheels to the bot workspace (rw mount), then `pip install --no-index --find-links <workspace>/_wheels mcp`.
16. **Boot warning "Memory provider 'holographic' loaded but no provider instance found"** after such a copy is a side effect of the resumed-session attach, NOT a broken provider — verify with `docker exec ... python -c "from plugins.memory import load_memory_provider; print(load_memory_provider('holographic'))"` (returns an instance). After closing open sessions the warning disappears on the next boot.
17. **add-bot.sh copies main's .env wholesale (line 82)** — it swaps the token/user lists but did NOT normalize `BALE_ALLOW_ALL_USERS` / `GATEWAY_ALLOW_ALL_USERS`, so main's `true` (or the `ture` typo) propagated to every bot profile, silently defeating the per-user allowlists the script carefully writes. Fixed in the script (they are forced to `false`); ALWAYS re-audit existing profiles: `grep -HnE "^(BALE|GATEWAY)_ALLOW_ALL_USERS" ~/.hermes/.env ~/.hermes/profiles/*/.env | grep -v "=false"` → must be empty, then `docker restart hermes-<name>`.

## Common ops

```bash
docker restart hermes-<name>                                          # reload config/.env
cd /home/oem/profiles-containers && docker compose up -d --force-recreate   # mount changes
docker logs --tail 100 hermes-<name> 2>&1
tail -f /home/oem/.hermes/profiles/<name>/logs/agent.log
```

New bot = `add-bot.sh <name> --token ... --user ...` — nothing in hermes_files
ever changes; the shared store is copied zero times.
